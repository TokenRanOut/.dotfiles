# technical-design-writing

## 文档目标

技术方案面向实施工程师和方案审查者，将已确认的需求与设计结论转化为有代码依据、可直接实施的改动说明。实施者应能明确目标、服务与模块归属、改动位置、关键规则和边界行为；审查者应能判断需求是否覆盖、设计是否一致、预期结果是否正确。

章节、表格和篇幅约束服务于实施理解，不为填满模板而写。文档不替代需求分析，不记录探索过程，不追求完整代码展开，也不把本可查证的关键实现留给实施者重新探索或推断。

## 使用入口

1. 读取 [技术方案模板](templates/technical-design.md)；更新或审查已有方案时同时读取原文。模板与写作规范以本 Skill 为准。
2. 编写或更新：检查调用方提供的需求范围、设计结论与证据是否覆盖本次实现；对可通过现有需求材料、代码、配置或依赖信息确认的事项，必须先完成查证，不得以“待确认”或“待核验”代替查证。缺少核验结果时由调用方补充相关查证，再组织正文。按下列规范填写模板，删除无内容的条件小节、模板提示和占位符，再完成正文自检。
3. 检查或审查：按下列规范及正文自检标准指出问题，给出可定位的原文位置、具体影响和修改建议；只把模板作为检查参考，不强制重套模板，不修改原文。用户明确要求修改时按编写或更新流程执行。

本 Skill 只约束技术方案文档的写作与审查。需求分析、证据核验、设计决策、探索委托、输出路径和保存授权由调用方负责；适用的项目编码规范直接复用，不在本 Skill 中重复定义。

## 模板与元数据

- 新文档使用模板中的 `requirement_title` 和 `requirement_scope`；范围分别为 `single-point` 或 `full-requirement`。
- 更新已有方案时保留其兼容的 frontmatter 字段；旧文档使用 `requirement_point_title` 时不为格式统一而强制改名。
- `date` 和设计日期填写实际设计日期，格式为 `YYYY-MM-DD`。
- `document_path` 填写调用方提供的文档路径。
- `analyzed_revisions` 使用调用方提供的实际分支或 Commit ID，不虚构版本信息。
- 保留有效的需求来源、标签及链接；正文占位符必须替换或删除，不输出模板说明注释。

## 范围与证据表达

- 正文只展开本次实施内容；必要的范围边界直接写成最终条件，不记录讨论过程或逐项列举已过滤的方案。
- 现状事实、风险结论和优化项必须有需求、项目代码、配置或已确认外部契约证据。
- 仅在完成相关查证仍无法确认，或因缺少访问权限、项目、版本等条件无法查证，且阻塞实现时，列入 What 的待确认事项；说明具体问题、已查范围或无法开展查证的条件、无法确认的原因、缺失信息及具体影响，不输出查证过程日志。需要业务方决策的事项明确提问，不用推测补齐。不阻塞本次实现的未知内容删除。
- 未确认、已排除或后续优化内容不得混入本次目标、流程、代码改动、示例和验收。后续优化仅在用户明确要求时另建独立方案。
- 现有代码引用使用 `ClassName.methodName() @ 完整路径:行号`；只保留直接影响实现的证据。理解本次实现所必需的既有契约、权限、事务及缓存规则，在对应位置简述或引用，不展开无关现状。

## 固定结构与篇幅

最终文档在标题下只能有四个顶层正文章节：`What`、`Why`、`How`、`Example`，沿用模板的编号与标题层级。不得增加摘要、实施、测试、决策记录、运维、风险清单、追踪矩阵或设计状态章节。

### 章节与小节的目的

按下表判断内容归属；目的说明只用于指导写作，不作为最终文档的固定段落。

| 章节或小节 | 要解决的读者问题 |
|---|---|
| What | 本次改动要达到什么目标，实施边界在哪里？ |
| 改什么 | 实施后哪些业务行为或能力发生变化？不提前展开实现细节。 |
| 范围 | 涉及哪些项目、模块和修改内容，哪些必要边界不变？ |
| 待确认事项 | 哪些问题经查证仍阻塞实施，需要补充什么信息或作出什么决策？ |
| Why | 哪些已核实的现状和必要约束使本次改动成为必要，它们如何影响设计？不重述目标或泛谈价值。 |
| How | 如何把目标落实为职责清楚、契约明确、能够实施的设计？ |
| 处理流程 | 从哪个入口开始，按什么顺序执行，关键分支和协作如何走向结果？ |
| 核心规则与实现 | 关键条件如何判断、数据和状态如何变化、采用什么机制，复用与新增能力如何协作？ |
| 辅助方法与规则 | 主流程省略了哪些必须补清的新增业务方法契约和逻辑？不机械罗列私有方法。 |
| 接口 | 调用双方如何依据服务归属、参数、结果、错误与兼容契约独立实现和联调？ |
| RPC 依赖版本 | 公共契约变化需要同步修改哪些依赖声明，保证提供方与调用方使用一致的契约？ |
| 数据库 | 持久化结构、约束和读写如何承载本次业务规则？ |
| 缓存 | 缓存内容和生命周期是什么，命中、失效及异常如何影响业务结果？ |
| 消息 | 生产与消费双方遵守什么结构和投递约定，异步处理及失败如何衔接业务流程？ |
| 代码改动 | 设计具体落实到哪些实际变更文件和符号，是否覆盖必要改动？不重复详细设计。 |
| Example | 用具体输入和可观察结果检验设计是否完整、一致，能够满足目标。 |
| 正常示例 | 正常输入如何经过关键处理和必要数据变化，得到目标结果？ |
| 边界示例 | 哪些关键条件、异常或边界会产生不同结果，预期结果是什么？ |

### 篇幅约束

| 内容 | 配额 |
|---|---:|
| What 目标 | 通常最多 3 条 |
| What 范围 | 通常最多 3 条；仅在影响实施理解时补充必要非目标 |
| Why | 通常最多 3 句；证据通常最多 3 行 |
| 核心规则 | 通常最多 8 条 |
| 单个处理场景 | 通常最多 8 步 |
| 单个接口用途 | 1 句 |
| 单个接口处理规则 | 通常最多 5 条 |
| 单个接口错误与兼容 | 通常最多 3 条 |
| 单个代码块 | 通常最多 40 行；复杂局部算法确有必要时最多 60 行 |
| Example | 通常 1 个正常示例；按独立场景和关键边界补充最少充分示例 |
| 待确认事项 | 通常最多 5 条；没有则删除 |

以上配额以单需求点或单个业务场景为默认粒度。完整需求包含多个场景时，各场景分别遵循步骤、规则和接口配额，并共享公共内容；What 目标和范围可按完整需求实际内容适当增加。接口字段、表字段和枚举值不受条目配额限制，必须完整。完整、可实施和可验收优先于篇幅目标；不得为满足配额遗漏需求点、业务规则、边界条件、字段或待确认事项。

## 表达要求

优先使用以下形式，避免大段文字描述：

| 内容 | 表达形式 |
|---|---|
| 业务规则 | 短句列表，一条一个规则 |
| 处理流程 | 编号短步骤，不使用流程表；关键分支配流程图 |
| 接口字段、数据结构、代码改动 | 表格 |
| 实现逻辑 | 目标语言的精简伪代码，突出关键调用 |

- 说明段落通常不超过 3 句；复杂内容拆成职责明确的小节，不通过遗漏必要信息缩短正文。
- 图表和代码已经表达的内容不再用长段文字复述；文字只补充未体现的必要约束。
- 表格仅用于接口字段、结构化数据、代码改动等需要逐项对照的内容；一般说明和业务流程使用短句列表或编号步骤。

1. 每句话只表达一个事实，每个流程步骤只描述一个动作。
2. 同一结论只出现一次；后文引用对应标题，不换一种说法重复。写作与更新遵循全局 `Writing and Updating` 原则；Why 只写当前问题和必要约束。
3. 禁止行业背景、通用技术常识、业务价值拔高、架构哲学和没有代码影响的分析。
4. 禁止使用“另一方面”“综上所述”“值得注意的是”“为了进一步提升”“从长远来看”“赋能”“抓手”等填充表达。
5. 禁止使用 `READY`、`PARTIAL`、`BLOCKED`、`DEFER`、“冻结”、“门禁”等状态或治理术语。符合“范围与证据表达”条件的未确认内容只写入待确认事项，不得进入目标、范围、流程、代码改动、示例或验收。
6. 禁止将性能、容量、部署、灰度、监控、告警、责任人和运维作为默认内容；需求明确要求且影响代码时，在对应 How 小节用一句具体规则说明。
7. 不输出独立测试矩阵、实施顺序或过程日志；可验收的预期结果写入 Example，不另建完成标准章节。

## How 内容要求

### 处理流程

- 按业务执行顺序写编号短步骤，不使用流程表；每步明确执行类/方法、输入条件、动作、数据变化或返回结果。
- 有关键分支、跨系统调用或状态流转的核心处理流程必须在文字步骤后提供 Mermaid 流程图，覆盖入口、关键动作、条件分支和结果；简单线性流程只保留文字步骤。图文必须一致。
- 多场景仅写真实差异；公共步骤只写一次。
- 事务、锁、幂等、降级和异常只有改变业务结果时才写入对应步骤。

### 核心规则与实现

- 核心规则必须给出已验证的具体实现机制。接口契约、数据读写、SQL 和中间件操作使用真实字段、完整 SQL 或精确操作；方法签名不能单独作为实现证据。
- 伪代码必须使用目标项目语言的语法、类型、方法签名、调用和控制结构，不使用自然语言步骤冒充代码；代码块语言标记与目标语言一致。
- 伪代码必须遵循项目代码规范及适用的编码 Skill，包括命名、职责划分、依赖注入、分支和异常处理；不因其为伪代码而放宽规范。
- 编排逻辑优先使用“薄编排伪代码”：写出入口、关键复用调用、拟新增业务方法名和数据流，不展开字段逐项赋值、Stream/集合转换、Getter/Setter、import 等机械实现。
- 使用职责明确的拟新增方法名，以及已核实的现有类型或明确标注的拟新增类型表达关键输入输出。方法注释只写影响实现的适用维度，如查询范围、必需参数、布尔条件、空值行为、批量限制、幂等键、事务或消息边界，不为无关维度补空说明。
- 已有类型和方法必须核实真实名称、签名和语义，已有方法调用明确标为复用；拟新增类型和方法必须明确标为新增或拟定，给出职责、目标路径及关键字段或签名，不得冒充现有能力。已有字段表或代码改动已覆盖的内容直接引用，不重复展开。
- 只省略机械实现，不省略关键业务规则、条件分支、异常行为和数据流；注释不能代替关键处理逻辑。
- 普通去重、映射、分批和对象组装不为展示而逐行展开，也不强制拆成无业务职责的小方法。复杂算法、关键并发、事务边界或容易写错的局部逻辑可提供目标语言真实代码。
- 禁止虚构现有类型或签名、`TODO`、`...`、遗漏关键分支，以及只有“查询数据、校验合法、处理结果”等无法指导实现的空泛注释。
- 所依赖的现有类型、签名或阻塞实现的规则，按使用入口先查证；仍无法确认时按“范围与证据表达”处理，不编造代码。

### 接口

- 只记录本需求新增、修改或删除的 HTTP、Dubbo 或其他接口。
- 每个接口独立小节，以 method/path 或完整方法签名为标题，标题下标注所属服务及所在项目/模块，再写 1 句用途。
- 所属服务指提供该接口的服务，不受 Provider、Consumer 是否发生变化的限制；服务名依据代码或配置核实，不从项目名推断。
- 新增或修改接口的请求和响应分表描述。字段列必须包含：字段路径、类型、是否必传或必返、是否允许 null、变化类型、业务语义、枚举或示例；请求字段同时标明实际参数位置。可选字段说明缺省行为；空字符串、空数组与 null 影响业务结果时说明其区别。
- 新接口列出全部字段；修改接口列出新增、修改和删除字段。接口整体删除时说明原契约、替代方式（如有）和删除后的调用结果，不强制列出全部原字段或正常请求响应示例。
- 新增或修改的对象及数组元素必须递归展开到全部叶子字段，例如 `result.items[].id`。顶层对象行不能代替内部字段，字段数量不设上限。
- 每个新增或修改接口给 1 组变更后的完整调用与结果示例，按真实传输形式展示；JSON 报文使用 JSON，路径、查询参数、请求头、表单、文件、流或 RPC 参数使用相应形式。无请求体或响应体时明确说明，不用空对象替代不存在的报文。
- 示例中的变化字段必须与差异字段表一致，未变字段可只出现在完整示例中；删除字段不得出现在变更后的报文中。
- Provider、Consumer 的变更以及鉴权、错误和兼容以本次变化与具体行为为主；直接影响实现的既有约束按“范围与证据表达”保留。
- 接口内部按用途分工：用途说明业务动作；处理规则只补充接口特有的条件和行为，公共规则引用核心规则；字段表定义数据契约；请求与响应示例展示具体调用形式；错误与兼容说明失败表现及对已有调用方的影响。
- RPC 公共契约新增、修改或删除时，在接口小节增加“RPC 依赖版本”表，列出 Provider 契约模块和全部受影响 Consumer 的依赖坐标、当前版本、目标版本及版本声明位置；目标版本沿用项目现有版本规则。版本规则经相关查证仍无法确认或缺少查证条件时，按“范围与证据表达”处理，不编造目标版本。仅 Provider 内部实现变化时删除本表。

### 数据、缓存与消息

- 新增的表、缓存值或消息结构给出完整定义；修改结构列出新增、修改和删除项，必要的既有约束按“范围与证据表达”保留。结构字段递归展开到叶子字段，说明类型、可空、业务含义，以及适用的必传、默认值或枚举。
- 跨服务或存在重名歧义时，明确数据库归属、缓存读写服务、消息生产和消费服务；名称依据代码或配置核实。
- 数据库写精确表字段、约束、SQL、索引和读写时机；只描述，不执行数据库操作。
- `CREATE TABLE` 必须使用全限定表名：`数据库名`.`表名`，数据库名和表名分别用反引号包裹。
- 字段注释只描述字段含义；状态字段注释可注明枚举值及简短中文含义。状态流转、隔离、覆盖等业务规则写在正文，不写入 SQL 注释。
- 缓存写完整 Key、Value、TTL、写入、覆盖、删除、命中、未命中和异常行为。
- 消息写准确 Topic/Queue、Producer、Consumer、投递时机和失败后的业务结果；字段使用独立字段表，新增消息列全量字段，修改消息列差异字段。
- 未涉及且不影响本次实现的类别删除，不写“无变更”。

### 代码改动

- 代码改动表只列实际新增、修改或删除的文件；新增能力写明职责，仅在理解实现所必需时说明现有能力的具体缺口。未修改的复用能力在流程或核心实现处标注并引用完整路径和符号，不加入改动表。
- 每个变更文件一行：项目、变更类型、符号、一句具体修改、完整路径；完整路径位于最后一列。
- RPC 公共契约新增、修改或删除时，代码改动清单必须包含 Provider 契约模块与每个受影响 Consumer 的版本声明文件。
- 不在清单中重复流程、接口字段或代码块内容。所有表格中的代码证据、代码位置、声明位置和完整路径放在最后一列。

## Example 要求

- 示例必须使用具体输入值，贯穿请求或事件、关键处理、实际涉及的数据变化和最终响应或可观察结果；不为无数据变更或无响应体的场景编造内容。
- 通常从 1 个正常示例开始；多个独立场景或关键边界具有不同结果时，补充最少充分示例，明确可观察的预期结果，不重复公共流程。
- 不使用抽象占位值解释业务。

## 正文自检

返回正文前自行修正，不把检查过程写入文档：

- 实施者能否据此定位入口、服务、模块和改动文件，并理解关键规则、契约、流程及结果；若仍需重新探索或推断方案本应明确的关键实现，补充设计或按核验规则说明真正阻塞的待确认事项。
- 各节是否完成其目的，Why 是否给出必要依据、How 是否落实 What、Example 是否验证目标及关键边界；是否存在为填模板而写或跨章节重复描述。
