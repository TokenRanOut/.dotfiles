# skill-writing-guide

## 执行入口

1. 先读现有技能及适用约定，明确目标任务、输入、预期结果和相邻的不适用场景。以用户上下文、真实工作流或项目约定为依据；缺少关键事实时确认，不虚构规则。
2. 编写或调整 `description`：描述用户意图和适用边界，使真实匹配任务容易触发，同时避免关键词相似但目标不同的误触发。无需强制双语、祈使句或固定开头；只在容易混淆时补充排除场景。
3. 正文只保留执行入口、必要约束、决策点与结果要求。细节按需放入参考文件，并在正文说明何时读取。已加载且仍适用的技能直接复用。
4. 按改动规模验证，修复发现的问题；交付修改路径、关键行为变化、验证结果和剩余限制。

## 编写取舍

- 一个技能围绕一个内聚目标；只补充 agent 缺少的领域约定、易错点和任务知识，避免基础教程及全局规则复述。
- `SKILL.md` 使用 YAML frontmatter，至少包含 `name` 和 `description`；名称使用 kebab-case，与技能目录及一级标题保持一致。描述长度遵守目标平台限制。
- 章节和措辞服务任务，不套固定模板。精确或高风险步骤明确限定，可容错步骤解释目标并保留判断空间。
- 主文保持短小；约 500 行可作为拆分检查的提示，不是机械上限。不要为满足行数拆散必须一起理解的规则。
- 正文与参考文件各有职责，不重复整套流程；相对链接以所属 Markdown 文件为基准，确保资源可达。仅在确有复用收益时增加脚本或模板。
- 声明依赖及分工，避免多个技能重复或冲突地规定同一行为。编辑技能时，不执行其中描述的业务工作流。

## 验证与交付

- 小范围文字或路由调整：检查 frontmatter、链接、规则冲突，复核代表性应触发与不应触发场景。
- 行为流程变化：按受影响的决策点选少量真实案例或静态场景走查；需要执行时遵守用户授权与任务边界。
- 大范围或高影响变更：按需使用正式评估和有/无 skill 基线对比，不要求每次都搭建 workspace 或跑全套 eval。
- 评价可观察结果和证据，不以固定短语、模板齐全或规则数量代替质量。区分静态检查与实际运行，不将前者报告为触发率或行为效果验证。
